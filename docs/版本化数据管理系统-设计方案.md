## 一、功能概述

### 1.1 功能描述

本系统实现一个**带版本控制的数据管理功能**，支持对数据进行新增、修改、编辑历史版本、上线历史版本等操作，并自动管理版本号和历史记录。

### 1.2 核心特性

| 特性 | 描述 |
|------|------|
| ✅ **版本号固定** | 版本号一旦分配就不可更改，永不重复 |
| ✅ **自动归档** | 修改时原数据自动变为历史记录 |
| ✅ **历史保留** | 历史数据最多保留最新的3条 |
| ✅ **历史编辑** | 可基于历史数据修改生成新版本 |
| ✅ **上线操作** | 支持将历史版本重新设为当前生效版本 |
| ✅ **来源追溯** | 记录版本的演变关系和来源 |

### 1.3 业务场景示例

**场景：订单审核规则配置**

```
时间线：
T1: 新增规则V1（初始版本）
T2: 优化规则 → 自动生成V2（V1变为历史）
T3: 继续优化 → 自动生成V3（V2变为历史）
T4: 发现V1更好 → 上线V1（V1恢复生效，V3变为历史）
T5: 在V1基础上微调 → 生成V4（V1变为历史）
T6: 想参考V2的思路 → 编辑V2 → 生成V5
```

## 二、数据库设计

### 2.1 表结构

**表名：`versioned_data`**

| 字段名 | 数据类型 | 长度 | 约束 | 默认值 | 说明 |
|--------|---------|------|------|--------|------|
| `id` | BIGINT | 20 | PRIMARY KEY, AUTO_INCREMENT | - | 主键ID |
| `business_id` | VARCHAR | 64 | NOT NULL, INDEX | - | 业务唯一标识 |
| `version` | INT | 11 | NOT NULL | - | **版本号（不可变）** |
| `status` | TINYINT | 4 | NOT NULL | 1 | 状态：1=生效，0=历史 |
| `name` | VARCHAR | 200 | NOT NULL | - | 数据名称 |
| `content` | TEXT | - | NULL | - | 数据内容（JSON/文本） |
| `remark` | VARCHAR | 500 | NULL | - | 备注说明 |
| `source_version` | INT | 11 | NULL | - | 来源版本号（编辑历史时） |
| `created_by` | VARCHAR | 64 | NULL | - | 创建人 |
| `updated_by` | VARCHAR | 64 | NULL | - | 最后修改人 |
| `created_at` | DATETIME | - | NOT NULL | CURRENT_TIMESTAMP | 创建时间（固定） |
| `updated_at` | DATETIME | - | NOT NULL | CURRENT_TIMESTAMP | 更新时间 |
| `effective_time` | DATETIME | - | NULL | - | 生效时间（上线时设置） |
| `deleted` | TINYINT | 1 | NOT NULL | 0 | 逻辑删除：0=正常，1=已删除 |

### 2.2 索引设计

```sql
-- 主键索引
PRIMARY KEY (id)

-- 联合唯一索引（保证同一业务下版本号唯一）
UNIQUE KEY uk_business_version (business_id, version, deleted)

-- 业务查询索引
KEY idx_business_status (business_id, status, deleted)

-- 时间查询索引
KEY idx_created_at (created_at)
```

### 2.3 建表SQL

```sql
CREATE TABLE `versioned_data` (
    `id` BIGINT(20) NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    `business_id` VARCHAR(64) NOT NULL COMMENT '业务唯一标识',
    `version` INT(11) NOT NULL COMMENT '版本号',
    `status` TINYINT(4) NOT NULL DEFAULT 1 COMMENT '状态：1=生效，0=历史',
    `name` VARCHAR(200) NOT NULL COMMENT '数据名称',
    `content` TEXT COMMENT '数据内容',
    `remark` VARCHAR(500) DEFAULT NULL COMMENT '备注说明',
    `source_version` INT(11) DEFAULT NULL COMMENT '来源版本号',
    `created_by` VARCHAR(64) DEFAULT NULL COMMENT '创建人',
    `updated_by` VARCHAR(64) DEFAULT NULL COMMENT '最后修改人',
    `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `effective_time` DATETIME DEFAULT NULL COMMENT '生效时间',
    `deleted` TINYINT(1) NOT NULL DEFAULT 0 COMMENT '逻辑删除',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_business_version` (`business_id`, `version`, `deleted`),
    KEY `idx_business_status` (`business_id`, `status`, `deleted`),
    KEY `idx_created_at` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='版本化数据表';
```

### 2.4 数据示例

假设业务ID为 `RULE_001` 的订单审核规则：

| id | business_id | version | status | name | remark | source_version | created_at | effective_time |
|----|-------------|---------|--------|------|--------|----------------|------------|----------------|
| 1 | RULE_001 | 1 | 0 | 订单审核规则V1 | 初始版本 | NULL | 2026-04-27 10:00:00 | 2026-04-27 15:00:00 |
| 2 | RULE_001 | 2 | 0 | 订单审核规则V2 | 优化金额判断 | NULL | 2026-04-27 12:00:00 | NULL |
| 5 | RULE_001 | 5 | **1** | 订单审核规则V5 | [基于V2编辑] 最新修改 | 2 | 2026-04-27 16:30:00 | 2026-04-27 16:30:00 |

**说明：**
- `status=1` 表示当前生效版本（每个 business_id 只能有1条）
- `status=0` 表示历史版本（最多保留3条）
- `source_version=2` 表示V5是从V2编辑而来的

## 三、核心业务逻辑

### 3.1 操作类型总览

| 操作 | 是否产生新版本？ | version变化 | status变化 | 说明 |
|-----|----------------|------------|-----------|------|
| **新增** | ✅ 是 | 新分配(MAX+1) | 1(生效) | 首次创建 |
| **修改** | ✅ 是 | 新分配(MAX+1) | 1(生效) | 归档当前+新建 |
| **编辑历史** | ✅ 是 | 新分配(MAX+1) | 1(生效) | 基于历史创建新版本 |
| **上线历史** | ❌ **否** | **保持不变** | 0→1 | 只切换状态 |

### 3.2 铁律：版本号的三不变原则

| 原则 | 说明 |
|------|------|
| **① 一旦分配，永不再用** | V1 用过后，不会有第二个 V1 |
| **② 一旦创建，永不修改** | version 字段只有 INSERT，没有 UPDATE |
| **③ 上线只改状态** | activate 操作只动 status，不动 version |

### 3.3 完整操作流程图

```
┌─────────────────────────────────────────────────────────────┐
│                     用户操作入口                              │
└────────────────────────┬────────────────────────────────────┘
                         │
         ┌───────────────┼───────────────┬───────────────┐
         ▼               ▼               ▼               ▼
   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │  新增     │   │  修改     │   │ 编辑历史  │   │  上线     │
   │ (Create) │   │ (Update) │   │ (Edit)   │   │(Activate)│
   └─────┬────┘   └─────┬────┘   └─────┬────┘   └─────┬────┘
         │             │             │             │
         ▼             ▼             ▼             ▼
    ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
    │产生新   │   │归档当前│   │归档当前│   │归档当前│
    │版本     │   │+产生新 │   │+产生新 │   │        │
    │V=MAX+1 │   │版本    │   │版本    │   │切换目标│
    │status=1│   │V=MAX+1 │   │V=MAX+1 │   │status  │
    └────────┘   └────────┘   │标记来源│   │0→1     │
                              └────────┘   └────────┘
                                              │
                                         清理旧历史
                                        (保留3条)
```

### 3.4 各操作的详细逻辑

#### 3.4.1 新增操作

**前置条件：**
- business_id 不存在

**执行步骤：**

```
输入: { businessId, name, content, remark }

步骤:
1. 校验 businessId 是否已存在
   ├─ 已存在 → 返回错误"该业务ID已存在"
   └─ 不存在 → 继续

2. 计算下一个版本号
   nextVersion = MAX(version) + 1 （或 1 如果是第一条）

3. 插入新记录
   INSERT INTO versioned_data (
       business_id = #{businessId},
       version = #{nextVersion},      ← 固定，后续不可改
       status = 1,                    ← 当前生效
       name = #{name},
       content = #{content},
       remark = #{remark} 或 "初始版本",
       created_by = #{currentUser},
       created_at = NOW()
   )

输出:
{
    "id": 100,
    "businessId": "RULE_001",
    "version": 1,
    "status": 1,
    ...
}
```

**SQL示例：**
```sql
INSERT INTO versioned_data 
(business_id, version, status, name, content, remark, created_by, created_at)
VALUES ('RULE_001', 1, 1, '订单审核规则', '{}', '初始版本', 'admin', NOW());
```

---

#### 3.4.2 修改操作

**前置条件：**
- business_id 存在且有当前生效版本

**执行步骤：**

```
输入: { businessId, name, content, remark }

步骤:
1. 查询当前生效的记录 (status=1)
   SELECT * FROM versioned_data WHERE business_id = #{id} AND status = 1 FOR UPDATE;
   
2. 将当前记录置为历史 (status=0)
   UPDATE versioned_data SET status = 0, updated_by = #{user} WHERE id = #{currentId};

3. 计算下一个版本号
   nextVersion = MAX(version) + 1;

4. 插入新记录 (新ID + 新version + status=1)
   INSERT INTO versioned_data (
       business_id = #{businessId},
       version = #{nextVersion},      ← 全新版本号
       status = 1,                    ← 当前生效
       name = #{name} 或 继承原名,
       content = #{content},
       remark = #{remark},
       created_by = #{currentUser},
       created_at = NOW()
   );

5. 清理超过3条的历史记录（详见第七章）

输出:
{
    "id": 101,
    "businessId": "RULE_001",
    "version": 4,                   ← 新版本号
    "previousVersion": 3,           ← 被归档的旧版本
    "message": "已从V3升级到V4"
}
```

**事务SQL：**
```sql
BEGIN TRANSACTION;

-- 步骤2: 归档当前版本
UPDATE versioned_data 
SET status = 0, updated_by = 'admin', updated_at = NOW() 
WHERE id = #{currentActiveId};

-- 步骤4: 插入新版本
INSERT INTO versioned_data 
(business_id, version, status, name, content, remark, created_by, created_at)
VALUES ('RULE_001', 4, 1, '订单审核规则', '{"new":"data"}', '修改说明', 'admin', NOW());

-- 步骤5: 清理历史（保留最新3条）
DELETE FROM versioned_data 
WHERE business_id = 'RULE_001' AND status = 0 AND deleted = 0
AND id NOT IN (
    SELECT id FROM (
        SELECT id FROM versioned_data 
        WHERE business_id = 'RULE_001' AND status = 0 AND deleted = 0 
        ORDER BY created_at DESC LIMIT 3
    ) temp
);

COMMIT;
```

#### 3.4.3 编辑历史操作

**前置条件：**
- 目标历史记录存在且 status=0

**核心思想：**
- **不修改原来的历史记录！**
- **创建一个全新的记录**（新ID + 新version）
- 通过 `source_version` 字段标注"我是从哪个版本演变来的"

**执行步骤：**

```
输入: { historyId, name, content, remark }

步骤:
1. 查询要编辑的历史版本
   SELECT * FROM versioned_data WHERE id = #{historyId};
   
   校验:
   ├─ 不存在 → 返回错误"记录不存在"
   └─ status=1 → 返回错误"该版本已是当前生效版本"

2. 记录来源信息
   sourceBusinessId = historyRecord.business_id
   sourceVersion = historyRecord.version      ← 记住这个！

3. 归档当前生效版本（同修改操作）
   UPDATE ... SET status = 0 WHERE status = 1;

4. 创建全新版本（不是修改历史记录！）
   nextVersion = MAX(version) + 1;
   
   INSERT INTO versioned_data (
       business_id = #{sourceBusinessId},
       version = #{nextVersion},          ← 全新版本号
       status = 1,
       name = #{name} 或 historyRecord.name,
       content = #{content},
       remark = "[基于V#{sourceVersion}编辑] #{remark}",
       source_version = #{sourceVersion},  ← ⭐ 标注来源！
       created_by = #{currentUser},
       created_at = NOW()
   );

5. 清理旧历史

输出:
{
    "id": 102,
    "businessId": "RULE_001",
    "version": 5,
    "sourceVersion": 2,                ← 来源版本
    "message": "已基于历史V2创建新版本V5"
}
```

**关键点：**
- 原来的历史记录（如V2）保持不变，仍可在历史列表中查看
- 新产生的V5通过 `source_version=2` 与V2建立关联
- 用户可以清楚地看到"V5是从V2编辑而来"

---

#### 3.4.4 上线历史操作 ⭐ 核心

**前置条件：**
- 目标历史记录存在且 status=0

**核心思想：**
- **只切换状态，不产生新版本！**
- version 号保持不变

**执行步骤：**

```
输入: { historyId }

步骤:
1. 查询目标历史版本
   SELECT * FROM versioned_data WHERE id = #{historyId};
   
   校验:
   ├─ 不存在 → 返回错误"记录不存在"
   └─ status=1 → 返回错误"该版本已是当前生效版本"

2. 记录目标信息
   targetId = target.id
   targetBusinessId = target.business_id
   targetVersion = target.version          ← 这个version保持不变！⭐

3. 查询并归档当前生效版本（如果有）
   currentActive = SELECT * WHERE business_id=#{targetBizId} AND status=1;
   
   IF currentActive EXISTS:
       UPDATE SET status = 0 WHERE id = currentActive.id;
       archivedVersion = currentActive.version;
   
4. 上线目标版本（只改status和effective_time！）
   UPDATE versioned_data 
   SET status = 1,
       effective_time = NOW(),
       updated_by = #{currentUser}
   WHERE id = #{targetId};
   
   ⚠️ 注意：version字段没有被触碰！

5. 清理旧历史（保留3条）

输出:
{
    "activatedVersion": 1,              ← 被上线的版本号（没变！）
    "archivedVersion": 4,              ← 被归集的原生效版本
    "message": "已将V1上线为当前生效版本，原V4已归档"
}
```

**SQL示例：**
```sql
BEGIN TRANSACTION;

-- 步骤3: 归档当前（如果有）
UPDATE versioned_data 
SET status = 0, updated_by = 'admin', updated_at = NOW() 
WHERE business_id = 'RULE_001' AND status = 1 AND deleted = 0;

-- 步骤4: 上线目标版本（只改这两个字段！）
UPDATE versioned_data 
SET status = 1,
    effective_time = NOW(),
    updated_by = 'admin',
    updated_at = NOW()
WHERE id = #{historyId} AND deleted = 0;
-- 注意：version 字段从未出现在 UPDATE 中！

COMMIT;
```

**✅ 核心保证：**
- `version` 字段**从未被 UPDATE**
- 只改变了 `status` 和 `effective_time`
- V1 永远是 V1，无论它被上线多少次

### 3.5 完整场景演示

#### 场景时间线

```
│     │          │ 1  │ 1        │ 0      │ V1 [历史]                        │
│     │          │    │          │        │                                  │
│ T4  │ ⭐上线V1 │ -  │ 1        │ 1      │ V1 [生效] ← 复活！（无新记录）    │
│     │          │ 3  │ 3        │ 0      │ V3 [历史]                        │
│     │          │ 2  │ 2        │ 0      │ V2 [历史]                        │
│     │          │    │          │        │                                  │
│ T5  │ 修改     │ 4  │ 4        │ 1      │ V4 [生效] ← 新！                 │
│     │          │ 1  │ 1        │ 0      │ V1 [历史]                        │
│     │          │ 3  │ 3        │ 0      │ V3 [历史]                        │
│     │          │ 2  │ 2        │ 0      │ V2 [历史]                        │
│     │          │    │          │        │                                  │
│ T6  │ 编辑V2   │ 5  │ 5        │ 1      │ V5 [生效] ← 新！（基于V2）        │
│     │          │ 4  │ 4        │ 0      │ V4 [历史]                        │
│     │          │ 1  │ 1        │ 0      │ V1 [历史]                        │
│     │          │ 3  │ 3        │ 0      │ V3 [历史] ← 将被删除（保留3条）  │

└─────┴──────────┴────┴──────────┴────────┴──────────────────────────────────┘
```

**关键观察点：**
- **T4时刻（上线V1）：没有产生新记录！** 只是把 V1 的 status 从 0 改成 1
- **版本号序列：** 1, 2, 3, 4, 5... **永远递增，永不重复！**
- **即使 V1 被反复上线，它始终是 V1**

#### 4.2.2 修改接口

## 五、查询逻辑

### 5.1 列表查询SQL

```sql
SELECT 
    vd.business_id,
    vd.name,
    -- 当前生效版本信息
    (SELECT v2.version FROM versioned_data v2 
     WHERE v2.business_id = vd.business_id AND v2.status = 1 AND v2.deleted = 0) as active_version,
    
    (SELECT v2.remark FROM versioned_data v2 
     WHERE v2.business_id = vd.business_id AND v2.status = 1 AND v2.deleted = 0) as active_remark,
    
    (SELECT v2.created_at FROM versioned_data v2 
     WHERE v2.business_id = vd.business_id AND v2.status = 1 AND v2.deleted = 0) as active_time,
    
    (SELECT v2.created_by FROM versioned_data v2 
     WHERE v2.business_id = vd.business_id AND v2.status = 1 AND v2.deleted = 0) as active_creator,
    
    -- 统计信息
    COUNT(*) as total_versions,
    SUM(CASE WHEN vd.status = 0 THEN 1 ELSE 0 END) as history_count
    
FROM versioned_data vd
WHERE vd.deleted = 0
  AND (#{keyword} IS NULL OR vd.name LIKE CONCAT('%', #{keyword}, '%') OR vd.remark LIKE CONCAT('%', #{keyword}, '%'))
GROUP BY vd.business_id, vd.name
ORDER BY active_time DESC
LIMIT #{offset}, #{pageSize};
```


## 七、历史清理策略

### 7.1 清理规则

- **保留数量：** 每个 business_id 最多保留 **3条** status=0 的历史记录
- **清理时机：** 每次产生新版本后立即清理
- **清理原则：** 保留**最新**的3条，删除**最旧**的
- **安全措施：** 使用软删除（deleted=1），可恢复

### 7.2 清理算法

```
算法伪代码:

FUNCTION cleanupOldHistories(businessId):
    
    // 1. 查询所有历史版本（按创建时间倒序）
    histories = SELECT * FROM versioned_data 
                WHERE business_id = #{bizId} 
                  AND status = 0 
                  AND deleted = 0
                ORDER BY created_at DESC;
    
    // 2. 判断是否需要清理
    IF histories.size() <= 3:
        RETURN;  // 不需要清理
    
    // 3. 计算需要删除的数量
    deleteCount = histories.size() - 3;
    
    // 4. 获取需要删除的ID列表（跳过前3条最新的）
    idsToDelete = [];
    FOR i FROM 3 TO histories.size()-1:
        idsToDelete.add(histories[i].id);
    
    // 5. 执行软删除
    UPDATE versioned_data 
    SET deleted = 1, updated_at = NOW() 
    WHERE id IN (idsToDelete);
    
    LOG("已清理{}条过期历史记录", deleteCount);
END FUNCTION
```

### 7.3 SQL实现

```sql
-- 方法1: 使用子查询（MySQL 8.0+）
UPDATE versioned_data 
SET deleted = 1, updated_at = NOW()
WHERE business_id = #{businessId} 
  AND status = 0 
  AND deleted = 0
  AND id NOT IN (
      SELECT id FROM (
          SELECT id FROM versioned_data 
          WHERE business_id = #{businessId} 
            AND status = 0 
            AND deleted = 0
          ORDER BY created_at DESC 
          LIMIT 3
      ) AS keep_ids
  );

-- 方法2: 使用JOIN（兼容更多MySQL版本）
UPDATE versioned_data vd
INNER JOIN (
    SELECT id FROM versioned_data 
    WHERE business_id = #{businessId} 
      AND status = 0 
      AND deleted = 0
    ORDER BY created_at DESC 
    LIMIT 3
) keep ON vd.id != keep.id
SET vd.deleted = 1, vd.updated_at = NOW()
WHERE vd.business_id = #{businessId} 
  AND vd.status = 0 
  AND vd.deleted = 0;
```

### 7.4 特殊情况处理

| 场景 | 处理方式 |
|------|---------|
| **刚上线的版本在被清理范围内** | 不清理！上线过的版本优先级更高 |
| **有source_version关联的版本** | 先检查是否有关联，如果有则保留 |
| **用户正在查看某条历史** | 延迟清理或给出提示 |
| **需要恢复误删的数据** | 通过 `deleted=0` 条件查询并恢复 |

## 八、并发安全机制

### 8.1 问题场景

**场景：** 用户A和用户B同时点击"修改"按钮

```
时间线:
T1: 用户A读取当前版本 V3 [status=1]
T2: 用户B读取当前版本 V3 [status=1]
T3: 用户A提交修改 → 归档V3，创建V4 [status=1]
T4: 用户B提交修改 → 归档V4（错误！应该是V3），创建V5 [status=1]

问题: 
- V3被归档了两次
- V4本应是用户A的新版本，但被用户B归档了
- 数据不一致！
```

### 8.2 解决方案：乐观锁 + 行锁

#### 方案一：行锁（FOR UPDATE）⭐ 推荐

```java
@Transactional
public Result<VersionedDataDTO> update(String businessId, UpdateRequest request) {
    
    // 步骤1: 加锁查询当前生效版本
    VersionedData currentActive = mapper.selectForUpdate(
        businessId  // SELECT ... FOR UPDATE
    );
    
    if (currentActive == null) {
        return Result.error("未找到当前生效版本");
    }
    
    // 后续操作...
}
```

**SQL：**
```sql
-- 加锁查询（其他事务必须等待锁释放）
SELECT * FROM versioned_data 
WHERE business_id = #{bizId} AND status = 1 AND deleted = 0 
FOR UPDATE;
```

**优势：**
- 简单直接
- 数据库层面保证原子性
- 适合并发量不大的场景

**优势：**
- 性能好（无锁等待）

#### 方案三：分布式锁（Redis）

对于分布式部署的场景：

```java
@Autowired
private RedissonClient redissonClient;

public Result<VersionedDataDTO> update(String businessId, UpdateRequest request) {
    
    String lockKey = "versioned_data:lock:" + businessId;
    RLock lock = redissonClient.getLock(lockKey);
    
    try {
        // 尝试获取锁（最多等待5秒，锁定30秒）
        boolean locked = lock.tryLock(5, 30, TimeUnit.SECONDS);
        
        if (!locked) {
            return Result.error("系统繁忙，请稍后再试");
        }
        
        // 执行业务逻辑...
        
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

**适用场景：**
- 多服务器部署
- 高并发环境
- 需要跨JVM的锁

### 8.3 推荐策略

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 单机部署，低并发 | **行锁（FOR UPDATE）** | 简单可靠 |
| 单机部署，高并发 | **乐观锁** | 性能好 |
| 多机部署，高并发 | **分布式锁（Redis）** | 跨服务协调 |
